# FIA Stewarding Decision Prediction — Dataset Feature Specification

## 1. Purpose

This document defines the feature schema for a machine learning system designed to predict the sanction a Formula 1 driver is likely to receive following an incident.

The central principle is:

> **Collect as much potentially useful information as possible in the raw dataset, but avoid redundant representations of the same fact and remove leakage before training.**

The recommended architecture is:

```text
RAW DATASET
    ↓
Data validation
    ↓
Leakage detection
    ↓
Feature engineering
    ↓
Feature selection
    ↓
MODEL DATASET
    ↓
Machine learning model
```

The raw dataset can be very wide. It is acceptable for it to contain 100+ columns. The model dataset can subsequently be reduced to the features that actually provide useful predictive information.

---

## 1.1 Authoritative Raw Schema

The canonical column layout for data collection is:

```text
documentation/f1_dataset_example.csv
```

- **Row 1:** column headers
- **Row 2:** example incident (`a001`, Monza 2021)
- **Row 3:** type legend — `*` = categorical, `**` = multi-value (comma-separated in one cell)

This file defines the **raw incident-centric** dataset. For machine learning, rows are later flattened to one row per driver under investigation (see `project_spec.md` §3). Do not remove multi-value columns from the raw CSV; they exist because a single incident often involves multiple drivers.

# 2. Core Design Principles

## 2.1 One column should represent one meaningful piece of information

Avoid encoding the same fact multiple times.

Bad:

```text
incident_type = collision
collision = True
```

If `incident_type` already identifies the incident as a collision, `collision` is redundant.

Better:

```text
incident_type = collision
contact_type = side_contact
initiating_action = overtaking
location_on_track = corner_exit
```

These describe different dimensions of the incident.

---

## 2.2 Prefer independent dimensions over arbitrary feature counts

Do not design the dataset around a target such as "exactly 50 columns."

Instead ask:

> What information about this incident could plausibly influence a steward's decision?

If 120 useful variables can be collected, the raw dataset can have 120+ variables.

Feature selection should happen later.

---

## 2.3 Derived features are not necessarily bad

Some features are mathematically related but can still be useful.

For example:

```text
lap = 52
total_laps = 58
laps_remaining = 6
race_completion_percentage = 89.7
```

These are related, but each can be useful to a model.

However, this should be distinguished from literal duplication:

```text
incident_type = collision
collision = True
```

The second example generally adds no new information.

---

# 3. Critical Rule: Point-in-Time Correctness

Every feature used by the prediction model must represent information that was available **before or at the moment of the incident**, not information generated by the FIA's final decision.

For every feature, ask:

> **Could this value have been known immediately after the incident, before the FIA made its final decision?**

If the answer is no, it should not be used as an input feature.

Valid examples:

```text
lap = 42
weather = wet
driver_position = 3
speed = 287
previous_penalties = 2
```

Potentially invalid:

```text
stewards_found_driver_at_fault = True
```

The latter is effectively part of the answer we are trying to predict.

---

# 4. Temporal Leakage

Historical features must only use information that existed before the incident.

For example, when predicting an incident at the 2024 British GP:

```text
2024 British GP
      ↓
Only races before British GP
      ↓
Calculate driver's previous incidents
      ↓
Make prediction
```

Do not calculate:

```text
previous_penalties
```

using penalties from later races in 2024.

This is especially important for:

- Driver history
- Championship position
- Championship points
- Similar historical incidents
- FIA precedent statistics
- Team standings

# 5. Recommended Dataset Architecture

Maintain multiple logical datasets/views rather than forcing everything into one table.

## 5.1 Raw dataset (CSV — incident-centric)

Contains all columns from `f1_dataset_example.csv`. One row per incident; multi-value cells for multiple drivers.

```text
dataset/csv/raw_incidents_{season}.csv
```

This is the human-editable data warehouse. Expect many cells to be empty after automated PDF extraction; enrichment fills them.

---

## 5.2 Enriched raw dataset (CSV)

Same schema as 5.1, after Ergast (and optionally FastF1) joins and validation.

```text
dataset/csv/processed_{season}.csv
```

---

## 5.3 Modeling dataset (Parquet — driver-centric)

Flattened to one row per driver under investigation. Used for ML after encoding.

```text
data/processed/incidents.parquet
data/processed/train.parquet
data/processed/validation.parquet
data/processed/test.parquet
```

Potential size after feature selection:

```text
30–70 useful features
```

---

## 5.4 NLP dataset

Keep long-form text separate from the tabular data.

```text
incident_id
document_id
fia_report
steward_reasoning
regulation_text
incident_summary
embedding
```

Stored under `data/interim/extracted_documents/`. Allows NLP experiments without forcing raw text into the tabular CSV.

## 5.5 Data Provenance — Where Each Feature Comes From

FIA steward PDFs are the **primary source for labels** but cover less than half the raw schema. Automated collection requires a multi-source pipeline.

### FIA Decision Documents Portal

**URL structure:**
```text
Season:  .../season/season-{YEAR}-{ID}
Event:   .../season/season-{YEAR}-{ID}/event/{Grand Prix Name}
PDF:     https://www.fia.com/sites/default/files/decision-document/{filename}.pdf
```

**Relevant PDF types:** Decision, Offence, Summons.

**Extractable from PDF text:**

| PDF field | Maps to column(s) |
|---|---|
| No / Driver | `drivers` (via car number → name mapping) |
| Competitor | `respective_teams` |
| Session | `session` |
| Fact | incident narrative; turn/corner hints → `sector` (indirect) |
| Offence | `incident_type`, `mentioned_article` (partial) |
| Decision | `penalty`, `superlicense_points_added` |
| Reason | `driver_at_fault` (label) |
| Document type | `investigation` (Summons = true) |

**Not in PDFs:** `lap`, weather, standings, positions, `severity`, most race context.

### Ergast F1 API (enrichment V1)

Provides: `season`, `round`, `circuit`, `country`, `rounds`, `num_teams`, driver/constructor standings and points before each race, driver nationality, car-number-to-driver mapping.

All standings/points columns must use values **before** the incident race (see §3–§4).

### FastF1 (enrichment V2+)

Provides: `lap`, `positions_of_involved parties`, `flag`, `safety_car`, `track_conditions`, `weather_conditions`, lap-level timing for `completion_percentage`.

### Manual / heuristic

`severity`, ambiguous `incident_type`, missing lap numbers, corner→sector mapping when not inferable.

### Pipeline reference

Full stage breakdown: `project_spec.md` §4 and `f1_project.md` Step 5.

Incident information should describe what physically or procedurally happened.

```text

lap_remaining
full_laps              # raw CSV name; total_laps in model layer
completion_percentage

```

### Definitions

| Feature | Raw CSV column | Description |
|---|---|---|
| `incident_id` | `incident_id` | Unique identifier for the incident |
| `season` | `season` | F1 season year |
| `round` | `round` | Championship round number |

| `full_laps` | `full_laps` | Total scheduled race laps |
| `completion_percentage` | `completion_percentage` | `lap / full_laps * 100` |
| `sector` | `sector` | Track sector 1, 2, or 3 |

Many incidents are relational. The model therefore needs information about the other driver.

```text
opponent_id
opponent_nationality
opponent_team
opponent_championship_position
opponent_championship_points
```

Relational features:

```text
same_team
championship_position_difference

```

Avoid unnecessary derived booleans when an underlying numerical feature already represents the relationship.

For example:

```text

```

may be more informative than simply:

```text

```

However, semantic features can still be tested experimentally if there is a defensible definition.

# 9. Driver Historical Behavior

This is one of the most important feature groups.

All values must be calculated using only events occurring before the incident.

## Career history

```text
career_incidents
career_penalties
career_reprimands
career_time_penalties
career_grid_penalties
career_disqualifications
career_license_points
```

Potential rate-based alternatives:

```text
career_incidents_per_100_races
career_penalties_per_100_races
```

Rates can reduce the problem caused by drivers having different amounts of F1 experience.

For example, a driver with 200 starts will naturally have more historical incidents than a driver with 20 starts.

# 11. Historical Incident Similarity

Historical precedent is one of the most interesting aspects of this project.

Potential features:

```text
previous_similar_incidents
previous_similar_penalties
average_similar_penalty
median_similar_penalty
most_common_similar_penalty
```

Example:

```text

average_similar_penalty = 6.8 seconds

```

However, similarity must be calculated without using the final sanction of the incident being predicted.

# 12. Similar Incident Retrieval System

A more advanced architecture can use embeddings and vector search.

```text
FIA Incident Text
       |
       v
Sentence Transformer
       |
       v
Vector Database
       |
       v
Similarity Search
       |
       v
Historical Precedents
```

Possible technologies:

- Sentence Transformers
- FAISS
- ChromaDB
- Other vector databases

The system could return:

```text
Top 5 similar historical incidents
```

and provide information such as:

```text
No penalty: 4
5-second penalty: 12
10-second penalty: 6
Disqualification: 1
```

This can then be transformed into features:

```text
precedent_no_penalty_probability
precedent_5sec_probability
precedent_10sec_probability
precedent_dsq_probability
```

# 21. Avoiding FIA Decision Leakage

Be extremely careful with features derived from the final steward decision.

Do not use a feature such as:

```text
stewards_found_driver_at_fault
```

if that conclusion is only known after the investigation.

Instead, use something like:

```text
investigation_reason
```

provided that the reason is available before the final sanction and does not itself encode the final conclusion.

The distinction is:

```text
WHAT HAPPENED?
        ↓
WHAT WAS INVESTIGATED?
        ↓
WHAT DID THE STEWARDS CONCLUDE?
        ↓
WHAT SANCTION WAS GIVEN?
```

If the target is:

```text
WHAT SANCTION WAS GIVEN?
```

the model should not be given:

```text
WHAT DID THE STEWARDS CONCLUDE?
```

unless the research question explicitly intends to predict the sanction conditional on the steward finding.

# 22. FIA Precedent Features

Historical precedent can be represented numerically.

Potential features:

```text
similar_precedent_count
precedent_average_penalty
precedent_median_penalty

```

```text
precedent_no_penalty_probability
precedent_5sec_probability
precedent_10sec_probability
precedent_grid_penalty_probability
precedent_dsq_probability
```

Example:

```text

```

```text

precedent_5sec_probability       = 0.52
precedent_10sec_probability      = 0.26
precedent_dsq_probability        = 0.04
```

Again, only historical precedents that existed before the incident should be considered.

# 27. Feature Selection

Do not manually delete potentially useful columns from the raw dataset just because there are many.

Instead use experiments.

Potential methods:

- Correlation analysis
- Mutual information
- Permutation importance
- SHAP
- Recursive feature elimination
- L1 regularization
- Model-based feature importance

For example:

```text
previous_penalties             ██████████
incident_severity              █████████
incident_type                  ████████
championship_context           ██████
weather                        ███
nationality                    █
```

If nationality contributes very little, that is an interesting finding.

If it contributes substantially, that does not automatically prove bias. It should trigger further analysis.

---

# 28. Nationality and Fairness Analysis

Nationality can be included as a feature, but it should be treated carefully.

Potential concerns:

- Nationality may correlate with team
- Nationality may correlate with era
- Nationality may correlate with media attention
- Nationality may correlate with driver popularity
- Some nationalities may have very few observations

A useful experiment is to compare:

```text
Model A:
without nationality
```

against:

```text
Model B:
with nationality
```

Then compare performance and feature importance.

This does not prove FIA bias, but it can identify correlations worth investigating.

---

# 29. Recommended Data Splitting Strategy

Do not rely exclusively on a random train/test split.

A random split can allow the model to learn from incidents that are extremely similar to those in the test set.

For a historical FIA project, a temporal split is more appropriate.

Example:

```text
TRAIN
2015 ─────────────── 2022

VALIDATION
2023 ─────────────── 2024

TEST
2025 ─────────────── 2026
```

This tests a much more interesting question:

> Can a model trained on historical FIA behavior predict decisions in future seasons?

---

# 30. Avoiding Duplicate or Near-Duplicate Incidents

Historical incidents may be highly similar.

For example, the same driver may appear in:

- Original investigation
- Revised decision
- Appeal
- Multiple documents describing the same event

These should not accidentally become multiple independent training examples.

The dataset should have a stable:

```text
incident_id
```

and, where necessary:

```text
decision_id
document_id
```

so that multiple documents can be linked to the same underlying incident.

---

# 31. Target Variable

The target should be defined independently from the input features.

Possible initial classification:

```text
0 = No penalty
1 = Minor penalty
2 = Major penalty
```

A more detailed classification can later distinguish:

```text
no_further_action
warning
reprimand
fine
5_second_penalty
10_second_penalty
drive_through
grid_penalty
license_points
disqualification
suspension
```

The detailed version will likely suffer from severe class imbalance, so a simplified target may be necessary for the first model.

---

# 32. Class Imbalance

Expected distribution:

```text
No penalty          ████████████████████
Minor penalty       ███████
Major penalty       ██
Disqualification    ▏
Suspension          ▏
```

Potential solutions:

- Class weighting
- Oversampling
- SMOTE
- Hierarchical classification
- Simplified target classes

Do not blindly use SMOTE on every feature type. It is particularly important to consider whether synthetic examples make sense for categorical and relational variables.

# 34. Final Recommended Philosophy

Do not ask:

> "How many columns should I have?"

Ask:

> **"What information about this incident could plausibly influence a steward's decision?"**

Then collect it — using FIA PDFs for labels, Ergast/FastF1 for context, and manual review where automation fails.

The raw CSV can be large and partially empty after first-pass extraction. The modeling dataset should be selective.

The strongest architecture is:

```text
FIA season URL → PDFs → parsed fields → raw CSV (f1_dataset_example schema)
                                              ↓
                                    enrichment (Ergast / FastF1)
                                              ↓
                                    processed CSV → flatten → model parquet
                                              ↓
                                    ML model / normative rules / comparison
```

The project should therefore prioritize:

1. **Rich raw data** (wide CSV, multi-value OK)
2. **Automated collection** (scraper + parser + enrichment)
3. **Point-in-time correctness**
4. **Leakage prevention**
5. **Non-redundant feature design** (in model layer)
6. **Temporal validation**
7. **Historical precedent**
8. **Explainability**
9. **Fairness/bias analysis**

The goal is not to build the model with the most columns.

The goal is to build a dataset that represents the incident as faithfully as possible, and then determine experimentally which information actually helps predict the FIA's decision.
